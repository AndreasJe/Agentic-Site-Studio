Failure analysis

When a run fails in the check runner, on staging or right after a production deploy, the failure is sent for analyst review. A larger model reads it, sorts the issues and recommends whether it should be let through. The analyst drafts; it never decides. {{heal.note}}

Fix and rerunThe analyst proposes the smallest fix as a new revision. It runs the full check runner again. Nothing is applied until a person approves it.
Hold for a personAnything on the security floor, low confidence, unclear cause, or a second failed fix. The analyst explains what it found and stops.

Guidelines for the analyst

It always
  1. Reads the failure as data: check output, logs, the diff since the last passing revision, guide.json and the section's job from the brief. Secrets are stripped before anything is sent.
  2. Sorts every issue by cause (generated code, content, brand rule, accessibility, speed and motion, infrastructure or a flaky test, a false alarm in the check), by severity (blocker, should fix, acceptable) and by confidence (high, medium, low).
  3. Shows its evidence: the log line, file and section behind each claim. No evidence, no recommendation.
  4. Keeps a fix to the smallest scope: only the failing sections, existing components first, within the brand guide.
  5. Ends with one plain sentence on what a person has to decide.
It never
  • Recommends letting through a failure on the security floor. Those can only be fixed.
  • Approves, publishes, rolls back or changes a check setting. It has no tools with consequences.
  • Makes a check pass by changing the check: no wider CSP or allowed domains, no higher budgets, no edited tests.
  • Changes an approved section quietly. A fix that touches one unlocks it, switches the affected checkmarks off and sends it back to review mode.
  • Tries more than two fixes for the same failure. After that it holds for a person.
Let through only when
  • The finding is advisory, not a hard gate.
  • It is a false alarm, or a deliberate break with a stated reason.
  • The analyst's confidence is high.
  • An Admin accepts it with a reason and their passkey. It is logged.
  • A flaky test or infrastructure hiccup may get one rerun of the same package, with no changes.

What the validators cover

Text in the page, and colours and fonts defined in CSS. Inside 3D scenes, canvases, raster images and video they can’t see, so those go on a manual review checklist in review mode.

Text over images gets a heuristic: a screenshot with the text hidden, the pixels behind the text box sampled, and the worst-case contrast computed. It only warns, never blocks.

The site’s Content Security Policy

Generated code must work under this policy: external scripts only, no inline scripts or event handlers, inline styles allowed. One approved video platform per site is added to frame-src.

default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; worker-src 'self' blob:; connect-src 'self'; font-src 'self'; media-src 'self'; frame-src [approved video platform]; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'

The security floor

Code validators, guide validators, secret scan, pinned libraries, SVG cleaning, HTML and link checks, the signature and hash checks in production, and the smoke test are always on Block. They can't be lowered here or in a project's settings.
